# Bazar.com - Distributed and Operating Systems Lab 1

A **two-tier online bookstore** with **three independent Python/Flask microservices**. The Frontend accepts client requests; Catalog maintains the four specified books; Order purchases books through Catalog's HTTP API and persists order history.

This completion preserves the original repository's Catalog conventions: **Catalog runs internally on port 5000**, supports `GET /search/<topic>`, `GET /info/<id>`, and **`PATCH /update/<id>` with `stock_delta`**. It does not replace Catalog's existing atomic stock-update implementation.

## Architecture

```text
Windows/Linux client
       |
       v
Frontend :5000 (public on 127.0.0.1:5000)
       | GET search/info       | POST purchase
       v                       v
Catalog :5000  <----------  Order :5000
       |    PATCH stock -1       |
       v                         v
Catalog SQLite volume      Orders SQLite volume
```

Docker Compose starts **three Linux containers** on one private network. Docker service names such as `catalog` work as internal DNS hostnames. Catalog is also published on `127.0.0.1:5001` for the original direct-Catalog tests and authorized inventory updates. Order is available only inside the Compose network.

## Repository structure

```text
catalog/       existing Catalog Flask app, SQLite schema, Dockerfile
frontend/      client-facing search, info and purchase REST endpoints
order/         NEW purchase processing and persistent order database
client/        NEW host-OS command-line client
compose.yaml   three containers, internal networking, two persistent volumes
tests/         existing Catalog tests + new isolated integration validation
docs/          design report, real execution output generated by validation
```

## Prerequisites

- Docker Desktop (Linux containers) or Docker Engine + Compose plugin
- Python 3 and `requests` on the **host** to run the CLI and validation
- Optional: `pytest` for the existing tests

Install host dependencies with `python3 -m pip install -r requirements-dev.txt` (on Windows, use `python`).

## Start the project

From the repository root:

```bash
docker compose up -d --build
docker compose ps
```

Expected: `catalog`, `order`, and `frontend` show **Up**. Starting order is not the same as readiness: wait briefly for services to initialize before requesting an endpoint.

Frontend: `http://127.0.0.1:5000`
Catalog (for lab testing): `http://127.0.0.1:5001`

### REST endpoints

| Service | Method | Path | Behavior |
|---|---|---|---|
| Frontend | GET | `/search/<topic>` | Forwards to Catalog; JSON list of `{id,title}` |
| Frontend | GET | `/info/<id>` | Forwards Catalog book details |
| Frontend | POST | `/purchase/<id>` | Forwards to Order |
| Catalog | GET | `/search/<topic>` | Search the two book topics |
| Catalog | GET | `/info/<id>` | `{title,quantity,price}` |
| Catalog | PATCH | `/update/<id>` | `{"stock_delta":-1}` OR `{"price":55}` |
| Order | POST | `/purchase/<id>` | Validate, decrement through Catalog, record order |
| Each service | GET | `/health` | Lightweight health response (where implemented) |

```bash
curl 'http://127.0.0.1:5000/search/distributed%20systems'
curl 'http://127.0.0.1:5000/info/2'
curl -i -X POST 'http://127.0.0.1:5000/purchase/2'
curl -i -X PATCH 'http://127.0.0.1:5001/update/2' -H 'Content-Type: application/json' -d '{"stock_delta":2}'
```

**Warning:** successful purchases and Catalog updates change persistent state. Out-of-stock purchases respond with `409`; unknown books with `404`. Catalog connection failures can produce `503` or uncertain-outcome errors.

### Command-line client (host OS)

```bash
python3 client/bazar_cli.py search 'distributed systems'
python3 client/bazar_cli.py info 2
python3 client/bazar_cli.py purchase 2
```

On Windows PowerShell, `python client/bazar_cli.py ...` also works when Python is installed. The CLI prints the returned information and purchase messages.

## Run isolated full validation (recommended)

The existing `tests/test_catalog.py` and `tests/test_concurrency.py` target `localhost:5001` and can **modify live inventory**. Do not blindly run them against important data.

Use the NEW isolated validation instead, from Ubuntu/WSL/Linux:

```bash
bash tests/run_validation.sh
```

The script creates a separate Compose project called `shaker_bazar_validation` with host ports **5100 and 5101** and separate **disposable databases**. It refuses to overwrite an existing test stack. It exercises:

1. Search/info, nonexistent book/topic and invalid purchase;
2. Price update, positive/negative stock update and insufficient-stock rejection;
3. Two simultaneous end-to-end purchase attempts for the final copy;
4. Exactly one completed order in Order SQLite;
5. Persistence across a Compose restart.

It writes **actual observed** client output to `docs/sample-output.txt`, saves container logs to `docs/service-logs.txt`, and deletes **only the isolated test project** including its test volumes. Run this command and review its successful output before claiming the tests have passed.

## Logging, persistence, and cleanup

```bash
docker compose logs --tail=100 frontend catalog order
docker compose restart                  # keeps named volumes
docker compose down                     # keeps named volumes
```

**Never use `docker compose down -v` on important data**: it removes the named SQLite volumes. The databases are mounted at `/data/catalog.db` and `/data/orders.db`.

## Important limitations and improvements

- Catalog's atomic SQL `UPDATE ... WHERE quantity + delta >= 0` prevents negative inventory when competing decrements race.
- Catalog decrement and Order insertion are two independent transactions. An unexpected failure between them can leave inventory and order history inconsistent. A timeout after a decrement can leave an uncertain outcome. This lab prototype does not use idempotency keys or a compensation/reconciliation service.
- Flask's included server is suitable for a demonstration, but production use should switch to a properly configured WSGI server and operational health checks.
- Authentication, payments, high-load stress guarantees, and distributed transactions are outside this Lab 1 prototype.
